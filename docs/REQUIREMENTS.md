# Requirements ledger

BudgetCents is the product. The original specification remains `docs/source/LedgerOne_Complete_Build_Prompt.txt` and is unchanged. LedgerOne is only that document’s historical title.

A row is **Implemented and verified** when the applicable interface, API, persistence, permissions, and error handling were exercised together. Older rows that say **Complete and verified** use that same bar. **Implemented, verification pending** means the code is present and a release build or unit test covers part of it, but that user flow was not run on that platform. **Implemented, awaiting external activation** means the adapter and its contract tests exist and the remaining gap is a production credential or a live endpoint. **Still unimplemented** means the workflow has no such adapter. A status row, a stored request, or a test sink is not awaiting activation. Sandbox bank fixtures are not a live aggregation provider. A provider accepting a test message is not confirmed delivery. **Partial** means one named slice is verified and another named slice is still open.

## Specification

### 01. One product

Sources: all seven reference apps. Web: BudgetCents shell. Android: `com.budgetcents.app`. API: service name `budgetcents`. Persistence: one household database. Verification: production page title and the Android application id in the release manifest. Remaining: the original prompt’s full behavior list is not all finished; this ledger keeps those items. Dependency: none. Status: **Partial**.

### 02. Web and Android platforms

Web is a responsive Vite app and an installable shell. The manifest uses the name BudgetCents, scope `/`, start URL `/`, and `standalone` display, with 192 and 512 PNG icons plus a maskable 512 icon. The production build lists the hashed JavaScript and CSS in the service worker precache and deletes older `budgetcents-` caches on activate. Only a navigation request may fall back to the shell. A missing script, stylesheet, image, or API response does not. Chrome 156 offered Install on `http://127.0.0.1:8833` on November 11, 2026 after a production load. ### 03. Interface

Web and Android share a teal and ink palette, plain formulas, and loading or empty copy on the screens that were built. The dashboard uses one card order for Safe to spend, Ready to Assign, Net worth, Age of money, Already given a job, Next bill, Needs review, Goals, This month, Upcoming, Alerts, and Recent. Identity warnings, budget warnings, the email verification notice, and setup stay outside that list. Safe to spend through Goals are Standard only. This month, Upcoming, Alerts, and Recent can be Standard or Wide and start Wide. Wide is a full row when the window is wider than 860 CSS pixels; a narrower window still shows the whole card and keeps the saved choice. Size changes presentation only.

Preferences are stored on the signed-in user for four device classes: `web-compact`, `web-desktop`, `android-compact`, and `android-expanded`. Compact is a window or screen 860 CSS pixels or dp wide, or narrower. Wider than that is desktop on the web and expanded on Android. The class follows the window size, not a browser name. Changing the window or rotating does not save a layout and does not replace another class. Web and Android are separate classes. A legacy `dashboardLayout` array is read as revision 0 and seeds every class with that order and visibility; a missing size uses the card default. The array is not rewritten until a class is saved, and a save replaces only that class. Writing a raw array is rejected. The server also rejects an unknown class, a duplicate id, an unsupported size, an unknown id, and a layout whose JSON is larger than 12,000 bytes. The retired id `overview` is dropped. A card added later is appended, visible, at its default size. The stored revision must match or the response is 409. A layout-only request updates `dashboard_layout` and leaves theme, onboarding, and the other profile columns unchanged. Read-only, coach, planner, and accountant members can save this personal layout. That does not let them change household records.

The web Customize dashboard dialog can drag a card by its handle, and Up and Down stay available. The handle uses `touch-action: none`; the rest of the page scrolls normally. Hide, Restore, Reset layout, and Undo keep the other properties. Hidden cards stay at the same index. The rendered order, the DOM order, and the keyboard order match. Undo is the previous layout for that user and device class, at most 20 deep, kept in this tab’s `sessionStorage` so a reload can still undo. It is removed when a different person signs in. A 409 clears that class’s stack and reloads the saved layout. Undo does not reverse a transaction, import, assignment, or reconciliation, and a layout request is not added to the transaction queue. Offline layout edits stay unsaved. The status says “Saving the dashboard layout.” and says saved only after the response. A failure says the change was not saved and offers Try again.

The Android home screen uses the same ids, order, sizes, and `PATCH /api/me` classes. Up, Down, Hide, Restore, Standard, Wide, Reset layout, and Undo dashboard layout are buttons. There is no drag. Wide is saved on a narrow screen and shown in one column. The undo stack is in memory for that process, up to 20, and is cleared when the signed-in user changes. A failed save is not described as a queued transaction. Shared dialogs move focus inside, keep Tab there, close with Escape, and restore the control that opened them. Row actions name the transaction, category, bill, paycheck, or fill. Hidden amounts use the accessible name “Amount hidden.” Reduced motion is already respected. This is not a WCAG 2.2 AA conformance claim. The records below are what was actually tested. Remaining: screen-reader speech, a keyboard pass of every route, and an Android device pass for these controls. Dependency: none. Status: **Partial**.

### 04. Onboarding, accounts, and preferences
